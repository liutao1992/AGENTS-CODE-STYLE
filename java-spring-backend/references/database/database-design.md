# 数据库设计规范

本文档定义数据库 Schema、表、字段、约束、索引、Migration 和数据库物理命名规范。

本文负责回答：

> 数据库结构本身应该如何设计和约束。

Java 模型职责读取：

- [应用分层与模型边界](../architecture/layering.md)

数据库字段与 Java 属性的映射方式读取：

- [MyBatis](../coding/mybatis.md)

SQL 编写与 PostgreSQL 查询规则读取：

- [SQL 与 PostgreSQL](sql.md)

核心原则：

> 数据库负责表达数据结构和数据完整性底线；Java 负责业务语义；两者通过明确映射隔离。

---

## 1. 数据库命名

数据库对象统一采用目标项目既定的：

```text
小写汉语拼音 + 下划线
```

适用于：

* 表；
* 字段；
* 索引；
* 约束；
* 序列；
* 视图。

例如已有：

```text
ryxx
ajxx
csxx
zjhm
rqsj
lqsj
cjsj
gxsj
```

不得在同一 Schema 无依据混用英文、拼音和中文命名。

---

## 2. 统一业务词汇

新增表、字段或数据库对象前必须搜索：

* Schema；
* Migration；
* SQL；
* Mapper XML；
* 数据字典；

确认项目是否已有相同业务概念的数据库词汇。

例如已有：

```text
zjhm  → 证件号码
rqsj  → 入区时间
lqsj  → 离区时间
csbh  → 场所编号
fzxbh → 分中心编号
```

后续继续沿用，不为同一概念重新发明另一套拼音缩写。

原则：

> 同一业务概念在数据库中只保留一套稳定表达。

---

## 3. 数据库与 Java 是不同命名边界

数据库物理命名不要求直接成为 Java 属性名。

原则上：

```text
Database
→ 项目统一数据库命名

Java
→ 英文业务语义
```

二者通过 Mapper / ResultMap 等显式映射。

本文不重复维护 ResultMap 和 TypeHandler 规则，详细读取：

- [mybatis.md](../coding/mybatis.md)

不要为了减少映射代码反向改变 Java 业务命名。

---

## 4. Schema 变更必须版本化

数据库结构必须通过项目正式的 SQL / Migration 机制管理。

禁止：

* 只在数据库客户端手工修改；
* 修改数据库后不保留 Migration；
* 依赖 ORM 自动创建生产 Schema；
* 使用 `ddl-auto=create` 维护生产表。

如果项目已有：

```text
Flyway
Liquibase
自定义 Migration
```

必须沿用现有机制。

---

## 5. 建表必须考虑完整约束

新增业务表时应明确：

* 主键；
* 数据类型；
* Null；
* 默认值；
* 唯一约束；
* 索引；
* 表注释；
* 重要字段注释。

数据库约束不应完全依赖 Java 代码补偿。

---

## 6. 主键

业务表原则上应具有明确主键。

主键应：

* 稳定；
* 唯一；
* 不依赖容易变化的业务展示值。

通常不要直接使用姓名、手机号、身份证件号码、场所名称等可变化或敏感业务字段作为系统主键。

具体主键生成方式必须遵循目标项目现有约定，不由 Skill 自行发明。

---

## 7. 字段类型

字段类型应表达真实数据语义，不为了方便全部使用 `varchar`。

例如：

```text
时间    → timestamp / date
整数    → integer / bigint
精确数值→ numeric
布尔    → boolean
动态 JSON→ jsonb（确有需求时）
```

不要把本应结构化的数据无依据序列化成字符串保存。

---

## 8. 字符串长度

`varchar` 长度应来自真实业务或协议约束。

不要无依据全部使用：

```sql
varchar(255)
```

编号、名称、证件、URL、备注等具有不同长度特征，应分别设计。

超长文本根据实际需求使用合适类型，例如 `text`。

---

## 9. NULL

字段是否允许 NULL 必须具有明确语义。

不要无意识全部：

```text
NULL
```

也不要为了避免 NULL 全部：

```text
NOT NULL DEFAULT ''
```

需要区分：

```text
NULL
空字符串
0
特殊日期
```

的业务含义。

例如“尚未离区”可以明确使用：

```text
lqsj = NULL
```

不要自行设计 `1970-01-01`、空字符串等特殊值代替未知状态。

---

## 10. 默认值

数据库默认值必须有真实业务或技术语义。

不要为了避免 NULL 随意增加：

```text
0
''
1970-01-01
```

如果状态或时间由数据库生成，必须确认这与 Java、API 和现有历史数据语义一致。

不得让 Java 默认值和数据库默认值表达不同业务含义。

---

## 11. 状态字段

状态字段应使用稳定编码或项目已有值体系。

不要直接把页面展示文案当作不可变数据库协议，除非项目本来如此设计。

Java 中如何表达状态属于 Java / 业务模型规则；本文只要求数据库值稳定且语义统一。

不得自行创造新的状态编码或兼容别名。

---

## 12. 时间字段

时间字段应表达明确业务语义，并沿用项目已有词汇。

例如已有：

```text
lssj → 录入时间
gxsj → 更新时间
rqsj → 入区时间
lqsj → 离区时间
```

不要新增长期含义模糊的：

```text
sj
time
date
```

跨时区业务需要明确数据库时区策略和应用约定。

---

## 13. 金额和精确数值

金额、比例和需要精确计算的数据应使用精确数值类型，例如 PostgreSQL `numeric`。

不要使用 `real` / `double precision` 表达需要精确财务语义的数据。

Java 对应精度处理读取 Java 编码规范。

---

## 14. 唯一约束

业务上必须唯一的数据，应优先使用数据库 UNIQUE Constraint 作为最终一致性防线。

不要只依赖：

```text
SELECT 判断不存在
→ INSERT
```

因为并发情况下可能产生竞争。

具体并发和事务处理读取：

- [transactions.md](../architecture/transactions.md)

---

## 15. 外键策略

是否使用数据库 Foreign Key 以目标项目既有架构为准。

如果项目统一不使用物理外键，仍必须明确关联关系和完整性维护方式。

不要在单个任务中无授权改变全项目外键策略。

---

## 16. 索引

索引服务真实查询和唯一性需求。

新增索引前分析：

* WHERE；
* JOIN；
* ORDER BY；
* 唯一性；
* 查询频率；
* 数据量；
* 写入成本。

不要看到字段就创建索引。

---

## 17. 联合索引

联合索引列和顺序应来自实际查询模式和 PostgreSQL 执行计划。

例如长期查询：

```sql
WHERE fzxbh = ?
  AND rqsj >= ?
  AND rqsj < ?
```

可以评估：

```text
(fzxbh, rqsj)
```

但不能仅凭这个例子机械创建。

SQL 执行计划分析统一读取 `sql.md`。

---

## 18. 不重复创建索引

新增索引前检查：

* 已有普通索引；
* PRIMARY KEY；
* UNIQUE Constraint 产生的索引；
* 已有联合索引是否覆盖需求。

禁止重复创建作用高度重叠的索引。

---

## 19. 表和字段注释

新增业务表和重要字段应提供有信息量的注释，说明：

* 业务含义；
* 状态含义；
* 特殊约束。

不要把复杂业务流程全部塞入数据库注释。

---

## 20. 删除语义

设计删除前必须确认：

```text
物理删除
还是
逻辑删除
```

如果项目使用逻辑删除，沿用已有字段和语义。

Codex 不得自行把 DELETE 改成逻辑删除，或反向修改。

---

## 21. 冗余字段

不要为了避免 JOIN 随意增加冗余字段。

确需冗余时必须明确：

* 数据来源；
* 更新责任；
* 一致性策略；
* 为什么收益大于维护成本。

无法说明维护策略时不应增加冗余字段。

---

## 22. 大字段

大文本、JSON、二进制等字段放入高频主表前应评估：

* 普通查询是否需要；
* 行宽和 IO；
* 是否应该拆表；
* 是否更适合对象存储。

不要无依据把文件内容直接保存到普通业务表。

---

## 23. Schema 兼容性

修改已有 Schema 时必须考虑：

* 历史数据；
* 线上兼容；
* 旧版本应用；
* Null / 默认值；
* 索引创建成本；
* 回滚或恢复方案。

未经明确需求不得：

* 删除已有字段；
* 改变已有字段业务含义；
* 修改主键语义；
* 随意放宽或收紧关键约束。

---

## 24. Codex 数据库设计检查

新增或修改数据库结构前检查：

1. 是否已有相同业务概念和数据库术语。
2. 命名是否沿用项目词汇。
3. 数据类型是否表达真实语义。
4. Null 和默认值是否有明确含义。
5. 是否需要主键、唯一约束或其他完整性约束。
6. 索引是否来自真实查询，是否与已有索引重复。
7. 是否提供必要表 / 字段注释。
8. 是否通过正式 Migration 管理。
9. 是否考虑历史数据和兼容性。
10. Java 映射是否应同步修改；需要时加载 `mybatis.md`，但不在本文重复映射规则。

最终原则：

> 数据库设计规范只维护数据库侧事实；Java 模型和 MyBatis 映射由各自专项规范维护。
