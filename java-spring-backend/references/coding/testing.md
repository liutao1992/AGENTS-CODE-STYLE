# 测试规范

本文档定义项目测试规范。

参考《阿里巴巴 Java 开发手册》的单元测试规约，并结合现代 Java、Spring Boot、MyBatis、PostgreSQL 项目实践进行筛选和调整。

核心原则：

> 测试验证业务行为、边界和失败语义，不为了覆盖率、Mock 数量或测试数量而测试实现细节。

> 好的测试应当自动化、独立、可重复，并能够在代码行为发生错误变化时稳定失败。

---

## 1. 行为变化需要测试

以下情况应优先补充或更新测试：

* 新增业务功能；
* 修改业务规则；
* 修改状态流转；
* 修复 Bug；
* 修改关键 SQL；
* 修改权限、租户或数据范围逻辑；
* 修改事务、一致性或并发行为；
* 修改重要 API 契约；
* 修改异常映射或关键失败语义。

不要求所有简单代码都机械增加测试；测试投入应优先覆盖业务风险和回归风险。

---

## 2. AIR 原则

单元测试应遵循 AIR：

```text
A — Automatic
    自动化

I — Independent
    独立

R — Repeatable
    可重复
```

### 2.1 Automatic — 自动化

测试必须能够由构建工具和 CI 自动执行。

禁止通过以下方式人工判断测试结果：

```java
System.out.println(...)
```

或者：

```text
运行测试
→ 人工看控制台
→ 人工判断是否正确
```

必须使用明确断言验证行为。

测试不得要求人工：

* 输入数据；
* 点击页面；
* 修改数据库；
* 启动某个本地临时服务；
* 观察日志后决定是否通过。

如果测试确实依赖外部环境，应明确归类为集成测试或端到端测试，并由项目已有测试环境管理。

---

### 2.2 Independent — 独立

测试之间不得存在执行顺序依赖。

禁止：

```text
testCreate()
   ↓ 产生数据

testUpdate()
   ↓ 依赖 testCreate

testDelete()
```

也不要在一个测试方法中直接调用另一个 `@Test` 方法来复用准备逻辑。

每个测试应自行准备所需前置条件，并自行保证必要的清理和隔离。

避免共享可变静态测试状态，例如：

```java
static List<String> sharedData = new ArrayList<>();
```

导致测试彼此污染。

---

### 2.3 Repeatable — 可重复

同一测试在相同代码和受控环境下重复执行，应得到相同结果。

不得依赖：

* 当前系统时间的偶然值；
* 随机数的偶然结果；
* 不受控制的外部网络；
* 本机绝对路径；
* 测试运行顺序；
* 上一次测试遗留的数据；
* 开发者本机数据库中的手工数据；
* 第三方服务当前是否在线。

对于时间、随机数、外部系统等不稳定因素，应通过依赖注入、Fixture、Mock、Stub、Testcontainers 或项目已有测试基础设施进行控制。

---

## 3. BCDE 测试设计原则

设计测试场景时应至少考虑 BCDE：

```text
B — Border
    边界

C — Correct
    正确输入和正常流程

D — Design
    设计 / 业务规则

E — Error
    错误和异常流程
```

### 3.1 Border — 边界

根据当前业务契约检查实际存在的边界，例如：

* 最小值 / 最大值；
* 空集合；
* 单元素集合；
* 分页首页 / 末页；
* 时间起点 / 终点；
* 日期跨天 / 跨月 / 跨年；
* NULL；
* 重复值；
* 数据顺序；
* 批量大小边界；
* 状态流转前后边界。

不得为了“覆盖边界”自行创造项目不存在的业务阈值。

---

### 3.2 Correct — 正常流程

至少覆盖核心正确输入能够得到预期业务结果。

测试不仅要证明：

```text
没有抛异常
```

还应根据场景验证真正业务结果，例如：

* 返回值；
* 状态变化；
* 数据写入；
* 调用条件；
* 重要副作用；
* 对外响应。

---

### 3.3 Design — 业务设计与契约

测试应来源于真实设计和业务规则，而不是根据当前实现反推测试。

例如需求规定：

```text
只有 PENDING 状态可以审核
```

测试应围绕这个业务契约验证，而不是只验证某个私有方法被调用了几次。

已有：

* API 契约；
* 状态机；
* 数据库约束；
* 权限规则；
* 事务约束；

都可以成为测试场景来源。

---

### 3.4 Error — 错误流程

必须考虑真实存在的失败场景，例如：

* 非法输入；
* 资源不存在；
* 状态不允许；
* 权限不足；
* 唯一约束冲突；
* 外部依赖失败；
* 数据库更新行数不符合预期；
* 并发冲突；
* 必要的异常传播和转换。

错误测试应验证预期失败语义，不要只写：

```java
assertThrows(Exception.class, ...);
```

在项目异常契约明确时，应尽量断言更准确的异常类型、错误码或关键业务结果。

---

## 4. Bug 修复

Bug 修复在合理情况下按照：

```text
复现 Bug
    ↓
增加失败测试
    ↓
确认测试能够稳定失败
    ↓
修复
    ↓
测试通过
```

测试应尽量锁定 Bug 的行为根因，而不是只覆盖某个实现分支。

避免：

```text
修复代码
→ 修改原测试使其通过
```

却没有证明问题不会再次出现。

---

## 5. 测试目录与组织

普通 Maven / Gradle Java 项目默认：

```text
src/main/java
→ 生产代码

src/test/java
→ 测试代码

src/test/resources
→ 测试资源
```

测试类 Package 通常与被测试代码保持对应，方便定位。

不得把单元测试放入生产源码目录。

如果目标项目已有不同的 source set、模块化测试目录或集成测试目录，以项目现有构建配置为准，不为了本文机械迁移目录。

---

## 6. 测试粒度

单元测试应尽量保持较小粒度，使失败时能够快速定位问题。

通常围绕：

```text
一个类
一个业务能力
一个明确行为
```

进行测试。

不要用单元测试承担完整跨系统链路验证。

如果测试需要同时验证：

```text
Spring 容器
+
数据库
+
多个 Bean
+
真实 SQL
```

它更接近集成测试，应按集成测试设计，而不是为了叫“单元测试”强行大量 Mock。

原则：

> 用单元测试快速验证局部业务行为，用集成测试验证框架、数据库和组件协作。

---

## 7. 测试命名

测试名称应描述业务行为和条件。

推荐：

```java
shouldRejectAuditWhenPlaceAlreadyRejected()
```

或者：

```java
audit_shouldRejectWhenPlaceAlreadyRejected()
```

同一模块保持统一。

避免：

```java
test1()
testAudit()
testMethod()
```

测试失败时，仅通过方法名就应尽量能够理解：

```text
什么行为失败了
+
在什么条件下失败
```

---

## 8. AAA 结构

复杂测试建议采用：

```text
Arrange
Act
Assert
```

例如：

```java
@Test
void shouldRejectAuditWhenPlaceAlreadyRejected() {
    // Arrange
    Place place = rejectedPlace();

    // Act + Assert
    assertThrows(
            PlaceStatusException.class,
            () -> place.audit(APPROVED));
}
```

AAA 的目标是让测试结构清楚，不要求每个简单测试机械添加三段注释。

如果测试中的 Arrange 远大于 Act / Assert，应检查 Fixture 是否过重、被测试代码职责是否过多或测试粒度是否错误。

---

## 9. 单元测试关注什么

单元测试重点验证：

* 业务规则；
* 状态变化；
* 参数边界；
* 异常分支；
* 重要算法；
* 分支选择；
* 依赖调用条件；
* 返回结果和重要副作用。

通常不需要测试：

* Java Getter / Setter；
* Lombok 生成的普通访问器；
* JDK 已保证的行为；
* Spring / MyBatis 框架本身已有充分保证的基础能力；
* 没有业务价值的简单字段复制；
* 无条件的一行转发方法。

测试价值优先于测试数量。

---

## 10. Mock 与测试替身

只 Mock 当前测试范围之外的依赖。

例如测试 Service 时，可以根据场景 Mock：

```text
Mapper
外部 HTTP Client
消息发送器
对象存储 Client
```

不要为了让测试通过而 Mock 被测试对象本身。

避免过度 Mock 导致测试实际上只验证：

```text
调用了 A
然后调用了 B
然后调用了 C
```

却没有验证业务结果。

交互断言适合验证有业务意义的协作，例如：

```text
状态不允许时不得执行 UPDATE
校验失败时不得调用外部系统
成功后必须发送一次必要消息
```

不要对所有内部调用顺序机械 `verify()`。

---

## 11. 为可测试性设计

代码难以测试时，应优先检查设计问题，而不是通过非常规测试技巧绕过。

可以通过：

* 构造器依赖注入；
* `Clock`；
* 明确的外部 Client 边界；
* 小而清晰的业务方法；
* 可替换的外部依赖；

提高可测试性。

不要仅为了测试把原本应该 `private` 的方法改成 `public`。

也不要默认通过反射直接测试私有方法。

如果一个私有方法包含大量需要独立验证的业务逻辑，应重新判断它是否暴露了职责过重或缺少合理抽象的问题。

原则：

> 优先测试可观察的业务行为；需要为了测试破坏封装时，先检查设计。

---

## 12. Service 测试

Service 测试重点验证：

* 业务流程；
* 业务校验；
* Manager / Mapper / Client 的调用条件；
* 异常分支；
* 业务结果；
* 不允许发生的副作用。

例如：

```text
状态不允许
→ 抛业务异常
→ 不执行 Mapper update
```

如果只需要单元测试，可以 Mock 外部依赖。

复杂数据库行为应使用集成测试。

---

## 13. Controller / API 测试

Controller 测试重点验证接口边界：

* HTTP 路由；
* 参数绑定；
* 参数校验；
* HTTP 状态；
* 项目统一响应格式；
* 异常映射；
* 权限边界；
* 序列化契约。

不要在 Controller 测试中重复完整 Service 业务测试。

目标项目统一响应默认可能使用 `ApiResponse<T>`，但具体结构以项目实际契约为准。

---

## 14. Mapper / SQL 测试

对于复杂 SQL，应考虑数据库集成测试。

特别是：

* PostgreSQL 特有 SQL；
* 动态 SQL；
* 多表 JOIN；
* 时间范围；
* NULL；
* 聚合；
* 分页；
* 唯一约束；
* 条件 UPDATE；
* 锁相关查询；
* ResultMap / TypeHandler 映射。

不要通过 Mock Mapper 来证明 SQL 正确。

Mock Mapper 只能证明上层在某个条件下调用了 Mapper，不能验证：

```text
SQL 语法
SQL 结果
数据库约束
实际映射
```

---

## 15. 数据库测试数据

数据库测试不得依赖开发者手工预先插入的数据。

禁止：

```text
测试前人工打开数据库
→ 插一条数据
→ 再运行测试
```

测试应通过可重复的方式准备自身数据，例如：

* 测试代码插入；
* SQL Fixture；
* 测试数据 Builder；
* Flyway / Liquibase 测试迁移；
* Testcontainers 初始化脚本；
* 项目已有测试数据工具。

测试数据必须符合真实数据库约束和业务前置条件，不要绕过正常规则制造无法在生产中出现的数据状态，除非当前测试就是验证异常脏数据处理。

---

## 16. 数据库清理与隔离

测试结束后不应给共享测试环境留下不可控脏数据。

可以根据项目测试架构选择：

* 事务回滚；
* 测试后清理；
* 每个测试独立 schema / database；
* Testcontainers 重建环境；
* 唯一测试数据前缀 / ID。

但不要机械给所有数据库测试加事务回滚。

如果测试目标本身就是验证：

* 提交；
* 回滚；
* 跨事务可见性；
* 锁；
* 隔离级别；

测试框架自动回滚可能掩盖真实行为，此时应根据测试目标设计数据清理方式。

---

## 17. PostgreSQL 测试

数据库测试应尽量使用与生产环境一致的数据库类型。

项目使用 PostgreSQL 时，不应默认使用 H2 验证 PostgreSQL 特有行为。

如果 SQL 强依赖 PostgreSQL：

```text
语法
类型
JSON / JSONB
数组
窗口函数
锁
隔离
索引行为
RETURNING
```

优先使用真实 PostgreSQL 测试环境或 Testcontainers。

---

## 18. 时间、随机数与环境变量

测试时间相关逻辑时，避免直接依赖：

```java
LocalDateTime.now()
Instant.now()
```

导致结果随运行时间变化。

复杂时间逻辑优先考虑注入：

```java
Clock
```

或项目已有时间抽象。

依赖随机值时，应确保测试能够控制或固定随机源。

依赖配置、环境变量、时区、Locale 时，应在测试中显式设置或通过项目测试配置提供，不能依赖开发者本机默认值。

---

## 19. 并发测试

并发问题不能仅靠：

```java
Thread.sleep(...)
```

证明正确。

涉及并发时应验证：

* 最终数据结果；
* 并发冲突；
* 更新行数；
* 乐观锁；
* 唯一约束；
* 重复执行；
* 必要的线程协调；
* 超时和失败路径。

优先使用：

* `CountDownLatch`；
* Barrier；
* Future；
* 项目已有并发测试工具；

建立明确同步点，而不是依赖“睡够几秒应该就执行完了”。

并发详细规则读取：

- [concurrency.md](../architecture/concurrency.md)

---

## 20. 事务测试

事务测试应验证最终数据状态和一致性，而不是仅检查存在：

```java
@Transactional
```

根据需求测试：

* 成功提交；
* 异常回滚；
* 多表一致性；
* 条件更新；
* 必要的隔离和锁行为；
* 跨事务可见性。

不要通过 Mock Mapper 证明事务行为。

事务详细规范读取：

- [transactions.md](../architecture/transactions.md)

---

## 21. 测试数据与 Fixture

测试数据应：

* 最小化；
* 含义明确；
* 与当前测试场景直接相关；
* 默认值清晰；
* 修改某个字段时能够看出该字段为什么重要。

避免每个测试构造几十个与目标行为无关的字段。

可以使用：

```text
Fixture
Builder
Object Mother
Factory Method
```

等方式减少重复，前提是它确实提高可读性。

不要把测试 Fixture 设计成另一个复杂业务框架。

---

## 22. 断言

必须使用明确断言。

禁止通过：

```java
System.out.println(...)
```

人工判断测试结果。

断言应关注关键业务结果。

推荐根据场景验证：

```text
返回值
关键字段
异常类型
错误码
最终数据库状态
重要依赖是否调用 / 未调用
```

不要为了增加断言数量验证大量与当前行为无关的字段。

失败信息应尽量能够帮助快速理解业务偏差。

---

## 23. 覆盖率

覆盖率是发现测试盲区的辅助指标，不是测试质量本身。

不得仅为了提高覆盖率：

* 给 Getter / Setter 写测试；
* 测试无业务价值的简单分支；
* 通过反射调用私有方法；
* 编写没有业务断言的测试；
* 排除真正重要但难测试的代码。

《阿里巴巴 Java 开发手册》中存在通用的覆盖率建议，但本 Skill 不把固定的：

```text
70%
100%
```

作为所有项目统一硬阈值。

如果目标项目已经通过：

```text
JaCoCo
SonarQube
CI Quality Gate
```

等配置了覆盖率要求，以项目现有门禁为准，不得擅自降低。

即使没有覆盖率门禁，也应优先覆盖：

* 核心业务；
* 高风险分支；
* Bug 回归；
* 权限和安全边界；
* 事务一致性；
* 数据库约束；
* 并发冲突。

原则：

> 追求关键行为被可靠验证，而不是追求一个漂亮的百分比。

---

## 24. 不得修改测试迎合错误实现

如果已有测试失败，首先判断：

```text
实现错了？
还是
需求真的变了？
```

只有需求、契约或业务规则明确发生变化时，才修改原有断言。

禁止：

* 删除失败测试；
* 注释失败测试；
* 弱化断言；
* 把精确异常改成 `Exception.class`；
* 添加无意义等待；
* 给测试加顺序依赖；
* 为了通过测试扩大 Mock 范围；

来让错误实现“变绿”。

---

## 25. 测试代码本身也要保持质量

测试代码是长期维护代码，不应因为位于 `src/test/java` 就降低基本质量要求。

避免：

* 大量复制粘贴；
* 巨型测试方法；
* 不清晰的测试数据；
* 魔法数字无法说明业务含义；
* 多个行为塞进一个测试；
* 测试失败后无法理解原因。

但也不要为了 DRY 把测试过度抽象成难以阅读的通用测试框架。

测试代码允许适度重复来换取场景独立和可读性。

原则：

> 生产代码优先消除业务重复；测试代码优先保证场景清晰，重复与抽象之间以可读性为准。

---

## 26. Codex 测试检查

修改代码后必须判断：

1. 是否改变了已有行为；
2. 是否属于新增业务能力或 Bug 修复；
3. 是否存在 BCDE 中的重要边界、正常、设计和错误场景；
4. 是否涉及 SQL、事务、权限、异常或并发；
5. 是否已有测试能够覆盖本次变化；
6. 新测试是否满足 AIR：自动化、独立、可重复；
7. 是否错误依赖人工数据库数据、外部网络或执行顺序；
8. 是否需要单元测试，还是实际需要数据库 / Spring 集成测试；
9. Mock 是否只隔离当前测试之外的依赖；
10. 是否真正验证了业务结果，而不是只验证调用次数；
11. 是否为了测试破坏封装或生产设计；
12. 是否需要测试 Null、边界、异常、回滚或并发冲突；
13. 数据库测试是否使用能够验证 PostgreSQL 真实行为的环境；
14. 是否为了提高覆盖率添加无价值测试或降低项目已有门禁。

执行测试后必须如实汇报：

```text
执行了哪些测试
哪些通过
哪些失败
哪些未执行
为什么未执行
```

不得声明没有实际执行的测试已经通过。

最终原则：

> AIR 保证测试可靠运行，BCDE 帮助设计完整场景；测试应保护真实业务契约和关键边界，而不是服务于覆盖率数字或当前实现细节。
