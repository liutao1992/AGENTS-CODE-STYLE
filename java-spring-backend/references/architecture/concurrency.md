# 并发规范

本文档定义多线程、线程池、异步执行、共享状态和并发控制规则。

本文负责回答：

> 是否值得引入并发、线程与资源如何管理、上下文和失败如何传播、共享状态如何保证正确性。

事务一致性读取：

- [事务](transactions.md)

核心原则：

> 不为推测性的性能收益引入并发；先证明操作独立且存在收益，再承担线程、上下文、异常和资源竞争的复杂度。

---

# 1. 引入并发前

必须确认：

* 操作是否真正独立；
* 是否要求共享事务或一致性快照；
* 是否依赖当前线程上下文；
* 是否存在共享可变状态；
* 数据库连接池、HTTP 连接池等资源是否能够承受额外并发；
* 并行收益是否大于线程调度和资源竞争成本。

不要因为多个操作“可以同时执行”就自动并行。

---

# 2. CompletableFuture / @Async

适合在以下条件同时成立时评估：

```text
任务彼此独立
+
不共享事务
+
上下文传播明确
+
资源容量足够
+
存在实际收益
```

特别禁止在一个已有数据库事务中，为了加速 Mapper 操作直接拆成多个线程并假设仍处于同一事务。

Spring `@Async` 的 Proxy 机制读取 `spring.md`。

---

# 3. Executor 与线程池

业务代码不得随意：

```java
new Thread(...)
```

或为单个功能机械创建独立线程池。

优先复用项目统一管理的：

```text
Executor
ThreadPoolTaskExecutor
```

线程池应明确：

* corePoolSize；
* maxPoolSize；
* queueCapacity；
* keepAlive；
* threadNamePrefix；
* rejectionPolicy。

生产代码谨慎使用 `Executors.newFixedThreadPool`、`newCachedThreadPool` 等隐藏容量语义的快捷工厂。

---

# 4. 队列和拒绝策略

任务队列必须考虑容量，避免无意识无界积压：

```text
生产速度 > 消费速度
        ↓
队列持续增长
        ↓
延迟 / 内存失控
```

拒绝策略必须与业务语义一致：

```text
直接拒绝
调用线程执行
明确降级
业务补偿
告警
```

重要任务不得无提示丢失。

---

# 5. 线程命名

线程池使用具有职责意义的名称，例如：

```text
place-stats-
case-import-
notification-
```

便于日志、Thread Dump 和故障定位。

---

# 6. 线程上下文

线程切换后不得假设以下上下文自动传播：

* Spring Transaction；
* SecurityContext；
* ThreadLocal；
* 当前登录用户；
* 数据权限；
* 租户；
* MDC；
* TraceId。

如果任务依赖这些信息，必须确认项目已有可靠传播机制。

不要随意手工复制所有 ThreadLocal。

---

# 7. ThreadLocal 生命周期

自定义 ThreadLocal 必须明确设置和清理边界。

在线程池中线程会复用，因此使用：

```java
contextHolder.set(context);
try {
    process();
} finally {
    contextHolder.remove();
}
```

避免异常路径导致用户、租户、MDC 等串线。

项目已有统一上下文机制时复用现有实现，不创建第二套。

---

# 8. 异步异常必须有明确语义

异步任务失败不能变成“无人感知”。

必须明确：

* 调用方是否等待结果；
* 失败是否影响主业务成功；
* 异常如何传播；
* 是否允许业务降级；
* 是否需要补偿、有限重试或告警。

子线程异常不会自动被主线程普通 `try/catch` 捕获，必须通过 Future、异步框架或明确异常通道传播。

## 8.1 `exceptionally()` 是恢复操作

`CompletableFuture.exceptionally(...)` 不只是“处理异常”，它会在回调返回正常值后，把原本的异常完成转换成正常完成。

例如：

```java
future.exceptionally(ex -> Collections.emptyList());
```

语义是：

```text
异步失败
→ 转换为空集合
→ 后续链路看到正常结果
```

这只有在业务明确规定“失败可以降级为空集合”时才正确。

禁止为了让流程继续机械返回：

```text
null
empty list
0
false
默认对象
默认状态
```

把系统失败伪装成正常业务结果。

如果失败应该影响调用方，应保持失败语义，例如通过等待 Future 时正确传播异常，或使用不会无依据转换结果的观察 / 记录方式。

如果确实允许降级，必须能够说明：

```text
为什么该失败可忽略
fallback 的业务含义是什么
调用方如何区分正常结果和降级结果（如果业务需要）
是否需要日志 / 指标 / 告警
```

原则：

> 异步异常恢复必须来自业务契约；`exceptionally` 不是自动吞异常的模板。

---

# 9. 等待 Future

使用：

```java
join()
get()
```

前明确：

* 是否可能长时间等待；
* 是否需要超时；
* 异常如何传播；
* 是否会长期占用请求线程；
* 是否真的存在并行收益。

不要：

```text
异步执行
→ 立即 join
```

却没有任何并行价值。

---

# 10. 协调工具

`CountDownLatch`、Semaphore、Barrier 等工具必须保证所有退出路径正确推进协调状态。

例如：

```java
try {
    process();
} finally {
    latch.countDown();
}
```

等待时还应明确超时、中断和子任务失败语义。

不要用复杂协调工具包装本来可以同步完成的简单流程。

---

# 11. 重试

不要看到异常就自动重试。

重试前确认：

* 故障是否瞬时；
* 操作是否幂等；
* 重试会不会放大数据库 / 下游压力；
* 次数、间隔和总等待时间是否有限。

通常不自动重试：

* 参数错误；
* 权限错误；
* 业务校验失败；
* 非幂等写操作；
* 原因未知的数据库写失败。

禁止无限重试和无依据固定重试次数。

---

# 12. 共享状态

优先：

* 方法局部变量；
* 不可变对象；
* 无状态 Service / Manager；
* 明确线程安全的数据结构；
* 数据库原子操作。

Spring Bean 默认通常是单例，因此不要把请求级临时状态保存在 Bean 可变成员字段中。

例如避免：

```java
@Service
public class PlaceService {
    private String currentPlaceId;
}
```

---

# 13. synchronized

`synchronized` 只能解决当前 JVM 内的互斥，不能自动解决多实例部署下共享数据库数据的一致性。

锁只围绕真正共享状态，避免锁住整个长业务流程。

锁内尽量避免：

* HTTP / RPC；
* 慢数据库调用；
* 文件 IO；
* 长时间计算；
* 无界等待。

---

# 14. Lock

成功加锁后必须在 `finally` 可靠释放：

```java
lock.lock();
try {
    doSomething();
} finally {
    lock.unlock();
}
```

`tryLock()` 必须确认确实获得锁后再释放。

需要多个锁时保持稳定一致的加锁顺序，降低死锁风险。

---

# 15. volatile 与原子类

`volatile` 主要保证可见性和部分有序性，不会让复合操作自动原子化。

例如：

```java
count++
```

即使 `count` 是 volatile，也不是原子操作。

需要原子更新时根据场景使用：

```text
AtomicInteger / AtomicLong
锁
并发集合
数据库原子操作
```

不要为了“线程安全”机械替换所有字段为原子类。

---

# 16. 数据库并发优先数据库一致性机制

涉及共享数据库状态时，优先根据真实场景使用：

* 条件 UPDATE；
* UNIQUE Constraint；
* 乐观锁；
* 悲观锁；
* 合适事务隔离。

不要默认使用 JVM 锁解决多实例数据库一致性。

具体规则读取 `transactions.md`。

---

# 17. 资源容量

增加业务并发度前检查下游容量：

```text
线程池并发
↓
数据库连接池
HTTP 连接池
第三方限流
CPU / 内存
```

线程数增加并不意味着吞吐一定增加。

如果瓶颈是数据库连接池或第三方限流，额外线程可能只增加等待和超时。

---

# 18. 不要推测性并发优化

没有基准、监控或明显串行瓶颈证据时，不因为“看起来可以并行”就把简单同步代码改成 CompletableFuture。

性能优化必须考虑额外：

* 可读性；
* 故障行为；
* 上下文；
* 线程池容量；
* 数据库连接；
* 测试复杂度。

---

# 19. Codex 并发检查

涉及并发时检查：

1. 是否有真实并发收益，而不是推测优化。
2. 操作是否独立，是否错误共享事务或快照。
3. 是否复用受控 Executor，线程池容量和拒绝策略是否明确。
4. SecurityContext、租户、数据权限、MDC 等上下文是否可靠。
5. ThreadLocal 是否在所有路径清理。
6. 异步异常是否可见；`exceptionally` 是否无依据把失败转换为正常 fallback。
7. Future 等待、超时和异常传播是否明确。
8. 重试是否幂等、有限且不会放大故障。
9. 单例 Bean 是否保存请求级可变状态。
10. Lock / synchronized 是否可靠释放、范围是否过大。
11. 是否错误使用 JVM 锁处理多实例数据库一致性。
12. 数据库 / HTTP 连接池等下游资源是否能够承受额外并发。

最终原则：

> 并发不是默认优化手段；只有独立性、收益、上下文、失败语义和资源容量都清楚时才引入。
