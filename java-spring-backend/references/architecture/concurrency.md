# 并发规范

本文档定义项目中多线程、线程池、异步执行和并发控制的使用规则。

参考《阿里巴巴 Java 开发手册》的并发处理规约，并结合现代 Java、Spring Boot、数据库事务和本 Skill 已有约定进行筛选与调整。

核心原则：

> 不为了推测性的性能优化引入并发。

> 先证明并发存在收益，再增加并发复杂度。

> 涉及共享数据库数据时，优先使用数据库提供的一致性机制。

> 线程安全不仅是“用了锁”，还包括线程池、上下文、共享状态、资源释放、异常传播和原子性边界都正确。

---

# 1. 并发使用原则

引入并发前必须先确认：

* 是否真的存在性能问题；
* 操作是否彼此独立；
* 是否存在共享状态；
* 是否涉及事务；
* 是否依赖线程上下文；
* 数据库连接池或其他资源是否能承受额外并发；
* 并发收益是否大于线程调度和资源竞争成本。

不要仅仅因为多个操作“可以同时执行”，就自动并行执行。

---

# 2. CompletableFuture

不要因为多个操作看起来互不依赖，就自动使用：

```java
CompletableFuture
```

使用前必须确认：

* 不要求共享事务；
* 不要求共享一致性快照；
* 不依赖当前线程上下文；
* 操作确实能够并行；
* 并行执行存在明确性能收益。

特别禁止：

> 在已有事务中，为了加速数据库访问，把 Mapper 操作直接拆到多个线程。

涉及事务时同时读取：

- [transactions.md](transactions.md)

---

# 3. 独立查询并发

对于无事务要求、彼此独立并且存在明确性能收益的查询，可以评估并行执行。

例如：

```text
统计 A
统计 B
统计 C
```

使用并发前必须确认：

* 查询之间完全独立；
* 不要求共享数据库快照；
* 不依赖当前线程事务；
* 数据库连接池容量允许；
* 查询本身确实是性能瓶颈。

多个查询不意味着并发一定更快。

例如三个很快的 SQL：

```text
串行：3ms + 3ms + 3ms
```

改成线程池后，还会增加：

* 线程调度；
* Future 创建；
* 数据库连接竞争；
* 上下文切换。

因此必须基于实际情况判断。

---

# 4. 线程创建

业务代码禁止直接使用：

```java
new Thread(...)
```

不得在业务代码中随意创建独立线程。

异步任务必须使用项目统一管理的 Executor。

---

# 5. 线程池

线程池应由项目统一配置和管理。

例如：

```text
Executor
ThreadPoolTaskExecutor
```

线程池应明确考虑：

* corePoolSize；
* maxPoolSize；
* queueCapacity；
* keepAlive；
* threadNamePrefix；
* rejectionPolicy。

不要隐藏线程池的容量和拒绝策略。

---

# 6. 线程池创建方式

生产业务代码中应谨慎使用：

```java
Executors.newFixedThreadPool(...)
Executors.newCachedThreadPool(...)
Executors.newSingleThreadExecutor(...)
```

避免这些快捷方式隐藏：

* 无界队列；
* 无限制线程增长；
* 内存风险；
* 任务大量堆积。

线程池参数应显式配置。

如果项目已经提供统一 Executor，不得为单个业务随意再创建一套线程池。

---

# 7. 队列必须可控

线程池任务队列必须考虑容量。

禁止在高并发业务中无意识使用无界队列。

无界队列可能导致：

```text
请求速度
   >
任务处理速度
   ↓
任务不断堆积
   ↓
内存持续增长
   ↓
OOM / 延迟失控
```

必须根据业务吞吐量确定：

* 队列大小；
* 最大线程数；
* 拒绝策略。

---

# 8. 拒绝策略

线程池必须明确拒绝策略。

不得忽略任务被拒绝的情况。

应根据业务确定：

* 直接拒绝；
* 调用线程执行；
* 丢弃；
* 业务降级；
* 记录并告警。

重要业务任务不得无提示丢失。

---

# 9. 线程命名

线程池必须使用具有业务含义的线程名称。

例如：

```text
place-stats-
case-import-
notification-
```

避免：

```text
pool-1-thread-1
```

明确线程名称有利于：

* 日志排查；
* Thread Dump；
* 性能分析；
* 故障定位。

---

# 10. 线程上下文

线程切换后，不得默认以下上下文自动传播：

* Spring Transaction；
* SecurityContext；
* ThreadLocal；
* 当前登录用户；
* 数据权限；
* 租户信息；
* MDC；
* TraceId。

如果异步任务依赖这些上下文，必须确认项目已经提供明确的传播机制。

不要随意手工复制 ThreadLocal。

---

# 11. 数据权限与异步任务

如果当前项目的数据权限、租户或登录信息依赖 ThreadLocal，异步执行前必须特别检查。

例如：

```text
主线程
  ↓
当前部门 / 当前用户
  ↓
CompletableFuture
  ↓
新线程
```

新线程默认不一定拥有主线程中的业务上下文。

因此不得直接假设异步查询仍然具有正确的数据权限。

---

# 12. ThreadLocal 生命周期

自定义 ThreadLocal 必须明确设置和清理边界。

在线程池环境中线程会复用，如果业务数据没有清理，可能导致：

* 后续请求读到上一个任务的数据；
* 用户、租户或数据权限串线；
* MDC / Trace 信息污染；
* 对象长期被线程引用造成内存泄漏。

设置 ThreadLocal 后应优先通过 `try/finally` 保证清理：

```java
contextHolder.set(context);
try {
    process();
} finally {
    contextHolder.remove();
}
```

不要只在正常流程末尾调用：

```java
contextHolder.remove();
```

因为中途异常可能导致清理逻辑无法执行。

如果项目已有统一上下文管理组件，应优先使用已有机制，不要自行维护第二套 ThreadLocal。

---

# 13. 异步异常

异步任务必须明确处理异常。

禁止出现：

```text
异步任务失败
     ↓
无人感知
     ↓
业务仍认为成功
```

例如使用：

```java
CompletableFuture
        .supplyAsync(...)
        .exceptionally(...);
```

或者在等待结果时正确传播异常。

如果异步结果影响业务成功状态，应明确设计：

* 等待结果；
* 异常传播；
* 补偿；
* 重试；
* 告警。

注意：子线程抛出的异常不会自动变成主线程普通 `try/catch` 能捕获的异常，必须通过 Future、任务框架或明确的异常通道传播。

---

# 14. 不要随意 join

使用：

```java
future.join();
```

之前应明确：

* 是否可能无限等待；
* 异常如何处理；
* 是否会占用请求线程；
* 是否真的比同步执行更有价值。

不要为了使用 `CompletableFuture`：

```text
异步执行
   ↓
立即 join
```

却没有实际并发收益。

---

# 15. CountDownLatch 等协调工具

使用 `CountDownLatch`、Semaphore、Barrier 等并发协调工具时，必须保证所有退出路径都正确释放或推进协调状态。

对于 `CountDownLatch`，任务完成通知优先放在 `finally` 中：

```java
try {
    process();
} finally {
    latch.countDown();
}
```

避免：

```java
process();
latch.countDown();
```

因为 `process()` 抛出异常后可能导致主线程永久等待或直到超时。

等待操作还应明确：

* 是否需要超时；
* 中断如何处理；
* 子任务异常如何传播；
* 部分失败是否允许继续。

不要用协调工具掩盖本来可以同步完成的简单流程。

---

# 16. 重试

不要看到异常就自动增加重试。

重试前必须确认操作具有幂等性。

可以考虑重试：

* 临时网络异常；
* 明确的瞬时故障；
* 乐观锁有限次数冲突。

通常不应自动重试：

* 参数错误；
* 权限错误；
* 业务校验失败；
* 非幂等写操作；
* 原因未知的数据库写失败。

必须限制：

* 重试次数；
* 重试间隔；
* 总等待时间。

禁止无限重试。

不得照搬固定的“至少重试 N 次”等阈值，重试策略必须结合业务冲突概率、成本和幂等性确定。

---

# 17. 共享状态

尽量避免多个线程共享可变状态。

优先：

* 局部变量；
* 不可变对象；
* 无状态 Service；
* 线程安全集合；
* 数据库原子操作。

谨慎使用：

```java
static mutable field
```

以及：

```java
shared HashMap
shared ArrayList
```

作为并发共享状态。

Spring Bean 默认通常是单例作用域，因此 Service、Manager、Component 中的可变成员字段也必须检查线程安全。

例如应避免把请求级临时数据保存为单例 Bean 的成员变量：

```java
@Service
public class PlaceService {
    private String currentPlaceId;
}
```

请求级状态优先使用方法局部变量或明确的上下文对象。

---

# 18. synchronized 的使用

`synchronized` 只能解决当前 JVM 内部的线程互斥。

例如：

```text
实例 A
   ↓
synchronized
```

无法限制：

```text
实例 B
```

因此，在多实例部署环境中，不要使用 JVM 锁解决共享数据库数据的一致性问题。

锁范围应尽可能围绕真正需要互斥的共享状态，避免为了省事锁住整个大方法。

锁内部应尽量避免：

* HTTP / RPC；
* 数据库慢查询；
* 文件 IO；
* 长时间计算；
* 无界等待。

原则：

> 锁保护共享状态，不保护整个业务流程。

---

# 19. Lock 必须可靠释放

使用 `Lock` 时，成功加锁后必须通过 `finally` 保证释放。

推荐：

```java
lock.lock();
try {
    doSomething();
} finally {
    lock.unlock();
}
```

加锁成功之后到进入 `try` 之间不要插入可能抛异常的业务调用。

使用 `tryLock()` 时必须先判断是否真正获得锁：

```java
boolean locked = lock.tryLock();
if (locked) {
    try {
        doSomething();
    } finally {
        lock.unlock();
    }
}
```

禁止在没有成功获得锁的情况下机械调用 `unlock()`。

需要等待锁时应评估是否需要：

* 超时；
* 可中断获取；
* 获取失败后的明确业务行为。

---

# 20. 多个锁必须保持一致顺序

一个流程需要获取多个资源锁时，必须建立稳定一致的加锁顺序。

例如统一：

```text
A → B → C
```

所有相关路径都应遵循相同顺序，避免：

```text
线程 1：A → B
线程 2：B → A
```

造成死锁。

新增多锁逻辑时应检查：

* 加锁顺序；
* 锁持有时间；
* 是否存在嵌套锁；
* 是否在锁内调用未知外部代码；
* 是否可以通过更简单的数据结构或数据库原子操作避免多锁。

---

# 21. volatile 不等于原子性

`volatile` 主要解决可见性和相关的有序性问题，不会自动把复合操作变成原子操作。

例如：

```java
volatile int count;
count++;
```

仍然不是线程安全的原子递增。

根据实际语义可以考虑：

* `AtomicInteger` / `AtomicLong`；
* `LongAdder`（高竞争统计场景）；
* 锁；
* 线程安全的数据结构；
* 数据库原子操作。

不要因为字段加了 `volatile` 就停止分析竞态条件。

双重检查锁等依赖可见性和重排序语义的写法必须严格遵循 Java Memory Model；如果项目已有更简单、安全的初始化机制，应优先复用，不手写复杂单例模式。

---

# 22. 线程安全单例与 Spring Bean

单例对象本身以及其暴露的方法都必须检查共享状态线程安全。

无状态 Spring Service 通常更容易安全复用；一旦引入可变成员状态，就必须回答：

* 多个请求是否会同时读写；
* 是否需要同步；
* 是否应该改为局部变量；
* 是否需要不可变对象；
* 是否存在更合适的状态存储位置。

不要因为“Spring Bean 是单例”就误认为其成员变量自动线程安全。

---

# 23. 随机数与并发

高并发线程中如果需要随机数，应避免所有线程竞争同一个普通 `Random` 实例造成不必要竞争。

在合适场景可以使用：

```java
ThreadLocalRandom.current()
```

但安全令牌、密码、验证码等安全敏感随机值不得使用普通伪随机方案，应使用项目已有安全随机机制或 `SecureRandom`。

不要仅为了性能猜测替换已有随机实现。

---

# 24. 定时任务调度

新代码不要为了简单定时需求机械使用老式 `Timer` / `TimerTask`。

需要 JVM 内调度时，优先使用项目已有调度框架，或根据实际需求使用：

```text
ScheduledExecutorService
Spring TaskScheduler / @Scheduled
```

必须明确：

* 单个任务异常是否影响后续调度；
* 是否允许任务并发重入；
* 执行时间超过调度周期时如何处理；
* 多实例部署是否会重复执行；
* 是否需要分布式调度或锁。

不要仅因为使用了调度线程池就假设业务任务天然可靠。

---

# 25. 数据库并发控制

涉及数据库共享数据的一致性时，优先考虑数据库机制：

* 唯一约束；
* 条件 UPDATE；
* 原子 SQL；
* 乐观锁；
* 必要时悲观锁。

例如：

```sql
UPDATE place
SET zt = #{targetStatus}
WHERE id = #{id}
  AND zt = #{expectedStatus}
```

通常比：

```java
synchronized (...)
```

更适合解决多实例数据库竞争问题。

数据库事务和锁的详细规范读取：

- [transactions.md](transactions.md)

---

# 26. 并发与连接池

数据库查询并发增加时，会同时增加数据库连接需求。

例如：

原来：

```text
1 个请求
→ 1 个连接
```

并行三个查询后可能变成：

```text
1 个请求
→ 同时占用 3 个连接
```

高并发下可能导致：

```text
HTTP 并发
×
单请求数据库并行度
>
连接池容量
```

最终造成连接池等待甚至超时。

因此数据库查询并发必须同时评估：

* HikariCP 最大连接数或目标项目使用的连接池容量；
* 接口并发量；
* 单请求并行查询数量；
* SQL 执行时间；
* 数据库承载能力。

---

# 27. 异步不是事务解决方案

不得通过：

```text
事务问题
   ↓
改成异步
```

规避事务边界。

也不得通过：

```text
事务太慢
   ↓
CompletableFuture
```

直接解决。

应先分析：

* SQL 是否慢；
* 事务范围是否过大；
* 是否存在锁等待；
* 是否存在不必要的远程调用；
* 是否真正适合并行。

---

# 28. 异步任务边界

适合异步的通常是：

* 不影响主业务结果的通知；
* 可延迟处理的数据；
* 独立统计；
* 独立日志处理；
* 明确可以最终一致的任务。

不适合直接异步的通常是：

* 当前业务必须成功的数据修改；
* 必须与主事务原子提交的操作；
* 强依赖当前 ThreadLocal 上下文的逻辑；
* 必须立即返回执行结果的操作。

---

# 29. Codex 并发判断流程

引入并发前判断：

```text
是否真的存在性能问题？
        ↓
操作是否彼此独立？
        ↓
是否不要求共享事务？
        ↓
是否不要求共享数据库快照？
        ↓
是否不依赖线程上下文？
        ↓
共享状态是否线程安全？
        ↓
线程池 / 连接池容量是否允许？
        ↓
异常、超时和资源释放是否明确？
        ↓
确认存在收益后再引入并发
```

如果任何一个条件不能确认：

> 优先保持同步实现。

---

# 30. Codex 编码检查

完成并发相关代码后检查：

* 是否真的需要并发；
* 是否为了推测性能使用 `CompletableFuture`；
* 是否直接使用 `new Thread(...)`；
* 是否自行创建线程池；
* 线程池参数是否明确；
* 队列是否有界；
* 拒绝策略是否合理；
* 线程名称是否有业务含义；
* 是否依赖没有传播的 ThreadLocal / SecurityContext；
* ThreadLocal 是否通过可靠边界清理；
* 数据权限是否能够正确传播；
* 单例 Bean 是否保存不安全的请求级可变状态；
* 异步异常是否得到处理；
* `CountDownLatch` 等协调工具是否在所有退出路径推进状态；
* 是否存在无限等待或缺少超时；
* 重试是否幂等且有限；
* Lock 是否只在成功获取后释放，并在 `finally` 中释放；
* 多个锁是否遵循一致加锁顺序；
* 锁范围是否过大，锁内是否执行远程调用或慢 IO；
* 是否错误认为 `volatile` 能保证复合操作原子性；
* 是否错误使用 `synchronized` 解决数据库并发；
* 数据库并发是否会耗尽连接池；
* 是否错误认为异步线程继承事务；
* 定时任务是否考虑异常、重入和多实例重复执行。

最终原则：

> 能同步解决的问题优先同步；只有明确存在收益，并且事务、上下文、共享状态、资源释放和容量边界都清楚时，才引入并发。
